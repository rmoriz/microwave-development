# Optional dedicated WebUI keypair

Date: 2026-11-04
Status: approved (2026-11-04)
Approach: A — one boolean switch, metadata store as source of truth, materialized to `data_dir`

## Intent

Chef's WebUI impersonation model lets a web front end act as any user by signing
requests with the server's `webui_priv.pem` while sending
`X-Ops-Request-Source: web` and the target user in `X-Ops-Userid`. Microwave
implements the verification half of that model but has no dedicated key: it
accepts the platform superuser's key instead (`middleware.rs`, comment "In this
harness the webui key is the superuser key").

That forces any WebUI such as
[cinc-console](https://github.com/cinc-project/cinc-console) to hold
`pivotal.pem` — full platform-superuser authority — just to browse an
organization. This design adds an optional dedicated WebUI keypair that is
generated by the server, stored in the metadata store, materialized as
`webui_priv.pem` / `webui_pub.pem` under `data_dir`, and trusted only for
`X-Ops-Request-Source: web` impersonation.

The feature is off by default. Turning it on changes the trust anchor for web
impersonation; it does not change ordinary signed-request authentication.

## Why now

- cinc-console 0.9 works against Microwave, but only by holding the superuser
  key. The console's documented deployment model expects a `webui_priv.pem`
  exactly like this.
- The store already has HA-safe secret primitives: `kvpair` with
  `set_secret_if_absent`, implemented for SQLite and PostgreSQL, and used by
  `ensure_object_store_secret` for exactly this kind of first-start bootstrap.
- `microwave-ctl` already exposes `show-secret` / `set-secret` / `remove-secret`
  and a rotation path for service credentials, so key export and rotation need
  no new storage surface.
- The backup private-file manifest already lists `webui_priv.pem` and
  `webui_pub.pem`; today they are only ever written by
  `import-knife-backup --secrets-dir`.

## Goals

- A config switch, `auth.webui_key`, default `false`, that enables a dedicated
  WebUI keypair.
- When enabled, the keypair is stored in the metadata store under
  `secret:webui:private_key` and `secret:webui:public_key`, so every replica in
  an HA deployment converges on one key.
- The private key is materialized to `<data_dir>/webui_priv.pem` (mode `0600`)
  and the public key to `<data_dir>/webui_pub.pem` (mode `0644`) on every
  start. The metadata store remains the source of truth.
- On first enable, an existing migrated `webui_priv.pem` is imported instead of
  generating a new key, so a server migrated from Chef keeps working with the
  same WebUI credentials.
- When enabled, `X-Ops-Request-Source: web` impersonation verifies against the
  WebUI public key only. The superuser key no longer impersonates.
- When disabled, behavior is exactly today's: web impersonation verifies
  against the superuser key.
- The operator can export the private key with
  `microwave-ctl show-secret webui private_key` or read the materialized file.
- The keypair can be rotated with the existing rotation command surface.
- The key survives `microwave-ctl backup` (database dump). With the default
  path it is also included in `--include-private-keys` archives via the
  existing manifest; a custom `webui_key_path` is rematerialized from the dump
  after restore.

## Non-goals

- Multiple simultaneously valid WebUI keys, overlap windows, or staged
  rotation. Rotation replaces the key; the old key stops working on the next
  server start.
- Per-user impersonation allowlists, org scoping of the WebUI key, or expiring
  keys. The key can impersonate any existing user, as in Chef.
- An HTTP endpoint that serves the public or private key.
- Encrypting the private key at rest beyond filesystem permissions and the
  database's own protection. Actor keys are stored the same way today.
- Changing client-key authentication, `/authenticate_user` ACLs, or the
  `chef-webui` client account.
- Automatically configuring cinc-console or any other WebUI.
- A key-size or algorithm knob. 2048-bit RSA, same as every other Microwave
  key.

## Anti-goals

- Enabling the feature must not leave the superuser key usable for
  `X-Ops-Request-Source: web`. Dual trust would defeat the purpose.
- The private key must never appear in logs, `microwave-server config` output,
  `_status`, metrics, error messages, or CLI output other than `show-secret`.
- A corrupt or unreadable stored key must fail startup with an actionable
  error. Silently generating a replacement would lock out every configured
  WebUI without warning.
- Default startup, the existing impersonation test, and all deployments that
  do not set the switch must behave exactly as before.
- A migrated `webui_priv.pem` must not be trusted while the switch is off.

## Constraints

- The key lives in the backend-neutral metadata store. Both SQLite and
  PostgreSQL must work; no SQLite-only shortcut.
- First-start bootstrap must be safe when several replicas start at once. Use
  `MetadataStore::set_secret_if_absent` for the private key; derive the public
  key from the retained private key.
- `AppState` is built after bootstrap in `bin/microwave-server/src/main.rs`, so
  bootstrap can return the public key for the state without adding an async
  lookup to the request path.
- The middleware change is limited to the existing `X-Ops-Request-Source: web`
  branch. The user-key verification loop and all ACL/org-membership checks stay
  untouched.
- `webui_priv.pem` materialization must be atomic: write a sibling temporary
  file, set its mode, then rename over the target.
- The file format is whatever `generate_rsa_keypair()` emits today (PKCS#8
  private PEM, SPKI public PEM). `parse_private_key_pem` already accepts
  PKCS#1 and PKCS#8, so migrated PKCS#1 files import unchanged.

## Approaches considered

### A — One boolean switch, store-backed, materialized (chosen)

`[auth] webui_key = true`, optional `webui_key_path`. Bootstrap reads the
stored private key, else imports the existing file, else generates. The public
key is derived and stored, both halves are written to `data_dir`, and the
middleware trusts only the WebUI key for web impersonation.

Pros: one switch, Chef-compatible files, HA-correct, migration-continuous.
Cons: enabling implicitly trusts a `webui_priv.pem` that happens to be present
when the store is empty. Mitigated by validating the PEM and documenting the
import rule.

### B — Tri-state `webui_key = "off" | "generate" | "import"`

Makes the first-enable choice explicit and avoids implicit import.

Rejected: more states than the requested on/off, and `import` still needs a
path, so the configuration surface grows without changing the steady-state
behavior.

### C — A separate `[webui]` table

`enabled`, `key_path`, and possibly `allow_superuser_impersonation`.

Rejected: every other authentication option lives under `[auth]`; a second
table implies a broader WebUI configuration surface that this change does not
have. The one part worth keeping — an explicit superuser fallback — is
deliberately not offered (see Anti-goals).

## Design

### 1. Configuration

Add to `AuthConfig` in `crates/microwave-config/src/config.rs`:

```toml
[auth]
# Generate and trust a dedicated WebUI keypair for X-Ops-Request-Source: web
# impersonation. Default false: web impersonation trusts the superuser key.
webui_key = false

# Optional. Where the private key is materialized. Default:
# <paths.data_dir>/webui_priv.pem. The public key is written next to it as
# webui_pub.pem. Must be absolute when set, and requires webui_key = true.
webui_key_path = "/etc/microwave/webui_priv.pem"
```

- `webui_key: bool`, default `false`.
- `webui_key_path: Option<PathBuf>`, default `None`.
- Environment overrides: `MW_AUTH__WEBUI_KEY` and
  `MW_AUTH__WEBUI_KEY_PATH`.
- Validation in `Config::validate`:
  - `webui_key_path` must be absolute.
  - Setting `webui_key_path` while `webui_key = false` is an error, not a
    silent no-op.
- `microwave-server config` shows both values. The private key is never part of
  the configuration, so nothing secret can leak there.

### 2. Bootstrap and storage

New function in `bin/microwave-server/src/bootstrap.rs`, called from
`main.rs` next to `ensure_superuser` (before `AppState` is built):

```text
ensure_webui_key(config, store) -> Result<Option<String>, Error>
```

When `config.auth.webui_key` is false: return `None`, touch nothing.

When true:

1. Read `secret:webui:private_key` from the store.
2. If absent, read the import source: `webui_key_path` when set, otherwise
   `<data_dir>/webui_priv.pem`. There is no fallback from a custom path to
   `data_dir`. Parse it with `parse_private_key_pem` to validate and use it as
   the candidate.
3. If absent and no file exists at the import source: `generate_rsa_keypair()`.
4. Retain the candidate with `set_secret_if_absent("webui", "private_key", …)`.
   The returned value is the key this deployment uses, even if another replica
   won the race.
5. Parse the retained private key and derive the public key. Store it with
   `set_secret("webui", "public_key", …)` so the stored pair can never drift
   from the private half.
6. Materialize both halves atomically at the configured path:
   - private: `0600`, parent directories created with `0700`
   - public: `0644`
   - rename over any existing file
7. Log one line with the public-key fingerprint (existing
   `public_key_fingerprint`) and no key material.
8. Return the public PEM for `AppState`.

Rules:

- The store always wins. If the file on disk differs from the stored key, the
  file is overwritten and an info line says so. An operator who wants to
  replace the key must use `set-secret` or rotation, not hand-edit the file.
- An unparsable stored or imported key is a startup error naming the secret and
  the fix: `microwave-ctl rotate webui` replaces the pair. Removing the secret
  alone does not regenerate, because the next start would re-import the
  materialized file; removing the secret **and** deleting the file is the
  documented clean-slate path.
- With `webui_key_path` set, the public key is always
  `<parent>/webui_pub.pem`; the private filename is whatever the path says.
- `--check` runs the same bootstrap as the other `ensure_*` functions, so it
  validates the stored key and the target directory.

`AppState` gains a `webui_key: Option<String>` field (the public PEM) with a
builder-style `with_webui_key(...)` setter. `with_metrics` and the test
constructors keep their signatures; `main.rs` calls the setter with the
bootstrap result. Tests that need the enabled path call it explicitly.

### 3. Middleware

Only the web branch in `authenticate_signed` changes:

```text
if not authenticated and X-Ops-Request-Source == "web":
    if config.auth.webui_key:
        require state.webui_key; if it is missing, fail closed (401) and log
        an error instead of falling back
        verify the signature with state.webui_key, then resolve X-Ops-Userid
        as a user (same org-membership and ACL behavior as today),
        key_name = "webui"
    else:
        today's superuser-key impersonation
```

The existing `impersonated_principal` helper is generalized to take the
verification key and the key name it should report. Everything after
authentication — org membership, `AuthContext`, ACL checks, action capture —
is unchanged.

Consequences:

- The config flag is authoritative, not the presence of a loaded key. A
  binary or test that enables `auth.webui_key` without populating
  `AppState.webui_key` must not silently re-enable superuser impersonation.
- A request signed with the WebUI key **without**
  `X-Ops-Request-Source: web` does not authenticate, because the WebUI key is
  only considered in the web branch.
- The WebUI key can name `pivotal` in `X-Ops-Userid`, which keeps
  `POST /authenticate_user` working for cinc-console with
  `CINC_AUTH_ACTOR=pivotal`. The request becomes the superuser principal; the
  existing `authorize_superuser_target` rules apply.
- The WebUI key cannot impersonate a client; impersonation resolves users only.
- `key_name` for audit/action metadata is the literal `webui`, not a key name
  that exists on any user.

### 4. CLI, export, and rotation

`KNOWN_CREDENTIALS` drives more than the three secret commands: it is also the
list `show-service-credentials` prints and `rotate-all` walks. The WebUI private
key must not join that list.

- Add a separate `EXTRA_CREDENTIALS` entry,
  `("webui", &["private_key", "public_key"])`. Credential validation and the
  single-group rotation lookup consult `KNOWN_CREDENTIALS` and
  `EXTRA_CREDENTIALS`; `show-service-credentials` and `rotate-all` keep walking
  only `KNOWN_CREDENTIALS`.
- `microwave-ctl show-secret webui private_key` is the documented export path.
  The materialized file is the convenience path.
- `set-secret webui private_key` validates the PEM and stores both halves
  immediately: parse the private key, derive the public key, write both
  secrets. `set-secret webui public_key` is rejected; the public half is always
  derived. This preserves the "stored pair cannot drift" invariant without
  waiting for a restart.
- `remove-secret webui private_key` removes only the private half; bootstrap
  will re-import the materialized file on the next start. The documented
  clean-slate path is `rotate webui`, or remove the secret and delete the file.
- Rotation: `rotate webui` regenerates the pair. Because the two halves are
  one keypair, handle it like the existing `push-jobs-server` special case:
  generate once, store both halves, print only `Rotated webui.private_key` /
  `Rotated webui.public_key`. `rotate-all` does **not** touch `webui`; rotating
  a WebUI key is an explicit, coordinated action. The command prints a warning
  that the server and every WebUI must be restarted/reconfigured, because the
  old key stops working.
- Rotation only changes the store. The running server keeps the public key it
  loaded at startup, and the materialized file is rewritten on the next start.
  Document that rotation is a restart operation.

### 5. Migration, backup, and upgrade behavior

- `import-knife-backup --secrets-dir` already preserves `webui_priv.pem` in
  `data_dir`. On the first start with `webui_key = true`, bootstrap imports it.
  No migration change is required.
- `microwave-ctl backup` dumps `kvpair`, so the key is in the database dump.
  With the default path, `--include-private-keys` already archives
  `webui_priv.pem` / `webui_pub.pem`. A custom `webui_key_path` is not in the
  fixed `data_dir` manifest; after restore the next start rematerializes the
  file from the database dump. Extending the archive to custom paths is out of
  scope for v1 and documented as such.
- Upgrade path: default `false` means no behavior change. An operator flips the
  switch, restarts, copies the materialized private key (or runs `show-secret`)
  into cinc-console, and removes `pivotal.pem` from the console.
- Downgrade path: turning the switch off restores superuser-key impersonation.
  A WebUI still configured with the dedicated key stops working until it is
  given `pivotal.pem` again.

### 6. Documentation

- `docs/deployment.md`:
  - data-directory table: `webui_priv.pem` / `webui_pub.pem` are generated when
    `auth.webui_key = true`, not only migrated.
  - auth configuration table: `auth.webui_key`, `auth.webui_key_path`.
  - a short "Web UI key" subsection covering the trust model, export, rotation,
    and the cinc-console handoff.
  - security section: when enabled, the console no longer needs superuser
    credentials; the WebUI key can still impersonate any user, so protect it
    like `pivotal.pem`.
- `docs/migration`-adjacent notes: first enable adopts a migrated
  `webui_priv.pem`.
- No homepage change.

## Testing

- `microwave-config`:
  - default is `false`; `true` parses; env override works.
  - relative `webui_key_path` is rejected; `webui_key_path` without
    `webui_key = true` is rejected.
- Bootstrap (`bin/microwave-server/src/bootstrap.rs` tests):
  - enabled with an empty store generates a pair, stores both halves, and
    writes files with `0600` / `0644`.
  - a second call reuses the stored key and rewrites identical files.
  - an existing `webui_priv.pem` is imported when the store is empty.
  - with a custom `webui_key_path`, only that path is imported; no fallback to
    `data_dir`.
  - a divergent file is overwritten when the store already has a key.
  - an invalid stored key fails with an actionable error.
  - two concurrent bootstraps converge on one key (mirror the existing
    object-store secret race test).
- `microwave-api/tests/keys_test.rs`:
  - enabled: WebUI key impersonates an org member; superuser key with the web
    header is rejected; WebUI key without the web header is rejected.
  - enabled but `AppState.webui_key` is missing: web impersonation fails
    closed with 401, never falling back to the superuser key.
  - disabled: the existing `webui_can_impersonate_an_org_member` test keeps
    passing unchanged.
  - enabled: WebUI key + `X-Ops-Userid: pivotal` passes `/authenticate_user`
    authorization for a normal user login.
- `microwave-ctl`:
  - `show-secret webui private_key` returns the materialized key.
  - `set-secret webui private_key` stores a matching public half; setting
    `public_key` directly is rejected.
  - `show-service-credentials` does not print the `webui` group.
  - `rotate webui` produces a matching pair and replaces both secrets;
    `rotate-all` leaves the `webui` secrets untouched.
- `cargo test --workspace` for the Rust change.

  the materialization helper is shared with `ensure_superuser`.
- Whether `webui_key_path` should be `PathBuf` or `String` in the config struct.
- Test helper naming and how `AppState` tests inject the public key.
- Precise log levels and message wording.
- Whether the `webui` credential group needs its own CLI alias instead of
  living in `EXTRA_CREDENTIALS`; v1 uses the generic secret commands.
